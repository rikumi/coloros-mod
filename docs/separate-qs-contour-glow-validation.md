# 分离控制中心轮廓光叠加修复

## 已确认的源码路径

参考 `../android-app-mods/com.android.systemui` 的 SystemUI 16.99.12（versionCode 169912）。设备上出现多层轮廓光以用户反馈为事实；本次没有采集设备画面。

- 分离磁贴 `OplusQSResizeableTileView` 持有 `bgDrawable`、`themeDrawable`，经 `TileTransitionDrawable` 作为 `getBg()` 的背景。`MixColorTileDrawable.Builder.build` 通过 `ViewTagUtils` 复用已有 drawable；没有发现模块反复新增 foreground 的代码。
- `MixColorTileDrawable.invalidatePath` 将 `strokeParamsTemplate` 应用于 `AutoBlurDrawable` 的 `ViewBlurProxy`。`draw` 在模糊、动画或形变分支中调用 `super.draw`，由 `AutoBlurDrawable.draw` 获取并绘制原生 `BackgroundBlurDrawable`，随后再绘制状态色块。
- 模块 `ActiveTileOutlineHooks` 在上述 `draw` 结束后，又按系统当前轮廓光参数绘制一份描边和顶部渐变。当原生描边已经可见时，两条路径会重复叠加。系统主题动画还可能让背景与主题 drawable 同时参与绘制，因此不能把“某 drawable 以前绘制过”作为永久跳过条件。

## 局部修改

仅修改 `ActiveTileOutlineHooks.java`，不新增设置或用户可见文案。

- 每次 `MixColorTileDrawable.draw` 建立独立的临时绘制上下文；通过同一代理实际返回的 `BackgroundBlurDrawable` 和硬件 Canvas，识别本次是否走了原生绘制路径。
- 仅针对分离磁贴及分离滑条的真实宿主继承关系：原生轮廓光已绘制且未被完全不透明色块覆盖时，跳过模块补画。原生描边缺失或被完全覆盖时保留既有补画。
- 保持合并控制中心的原有补画判定；不修改系统描边参数、模糊配置或视图 foreground，不向 drawable 链增加层。
- 判定每帧更新，不缓存“这是分离模式”或“已经绘制”状态；宿主重绑定后重新分类。临时上下文在 `finally` 中恢复或移除，包含异常及嵌套绘制路径。没有增加监听器、动画或热加载后需要恢复的持久渲染状态。
- 模块轮廓光开关仍默认关闭，关闭时不补画；系统开关仍由既有有效描边参数检查控制，不强行启用系统效果。自定义颜色仍只临时替换绘制色块，并在结束后恢复。

## 针对性非构建验证

从修改后的源码提取实际 before/after hook、原生代理观察回调、宿主分类及绘制上下文判定，在独立 Java 模拟环境执行：

- 连续 100 次分离绘制，只保留模拟的原生层。
- 不同透明度色块、完全不透明色块、原生 drawable 缺失时的补画分支。
- 系统与模块开关、激活态颜色覆盖、异常清理、代理身份隔离、软件 Canvas 排除。
- 同一 drawable 在分离与合并宿主之间重新绑定、嵌套绘制及绘制中途关闭模块开关时的上下文恢复。
- 合并模式保持原判定；有效遮罩 alpha 使用与 ROM 相同的运算式。

以上模拟检查及 `git diff --check` 均通过。模拟只验证分支和状态清理，不代表真实 RenderNode、GPU、深浅主题或框架热加载已经通过设备验收。未执行 Android 构建、安装或设备操作。

## 设备验收清单

由统一构建后手动验收：

1. 系统轮廓光开启，模块轮廓光关闭：首次展开分离控制中心，确认原生视觉未改变。
2. 开启模块轮廓光，分别检查普通磁贴、Wi-Fi/蓝牙横向磁贴及亮度/音量滑条；确认可见描边没有重复加亮或多道边缘。
3. 反复展开、收起至少 20 次，并切换磁贴激活状态，观察过渡动画及结束状态是否叠加。
4. 在深色和浅色主题中重复，分别切换系统轮廓光开关；系统关闭时不能出现模块强行保留的轮廓光。
5. 切换模块轮廓光、自定义激活颜色；模块关闭后应恢复系统视觉，开启不透明自定义颜色时仍可正常补画。
6. 如启用框架热加载，执行正常模块更新后重复以上项目，确认旧回调已由框架卸载；本次没有主动触发热加载。
7. 回到合并控制中心，核对轮廓光、颜色及圆形图标背景原有行为。

目前没有代码实施阻塞。实际设备上是否恰好保留期望的一层，仍以统一构建后的上述验收为准。
